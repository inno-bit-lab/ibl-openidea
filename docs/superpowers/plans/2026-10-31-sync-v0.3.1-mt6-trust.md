**Goal:** bring upstream's project trust (#517) and its test fix (#571) into `next/v0.3.1`, and classify and protect every command the fork adds:

## Review Focus

1. No fork command is allowed in `restricted_command_allowed` by a prefix. `agent_complete` is the only fork command that still needs trust.
2. `ops::vcs::ignored` never calls `apply_git_executable` for an untrusted project. The Git binary is process-wide, so one call would hand the project's executable to every later Git command in any window.
3. The execution gate checks the flag and clones the token under one lock, before the temporary directory and the spawn. Revoke and `shutdown()` both set the flag to false and cancel the token under that lock; only `set_execution_allowed(true)` reopens it. `complete()` checks `epoch.is_cancelled()` again right before the connector call and awaits the token for the whole session, not only the prompt. No test reaches the window between the gate and that re-check: the fake connector runs after the re-check, and provider loading and directory creation offer no seam. The review therefore checks the order in `complete()`: gate, `provider::load`, temporary directory, re-check, connector.
4. Every negative test has a positive control in the same test: the witness really runs once the project is trusted. Each Git channel has its own marker and its own control.
5. Fork edits to upstream files stay minimal (one classification call in `trust.rs`, `set_execution_allowed` calls in `trust.rs` and `project.rs`), and the delivery lists them as sync cost.

## 1. Context and goal

Upstream #517 opens projects in Restricted Mode until the user trusts them. It gates commands in two places:
- the local Tauri invoke handler (`src-tauri/src/lib.rs` at `2c9a6470`, the `invoke_handler` closure, with `remote_dev.rs` `Connection::authorize_command` for remote windows);
- the remote dispatcher (`crates/ide-host/src/rpc.rs`, `ServerHandler::on_request`).

Both call `trust::restricted_command_allowed` (trust.rs:149-285). Any other command needs the window's project to be trusted, through `Host::authorize_command` (trust.rs:288-293). A window without a project, Welcome or its Settings window, therefore gets only the allowlisted commands.

The fork registers three commands upstream does not know: `agent_complete`, `agent_set_args` and `vcs_ignored` (`src-tauri/src/commands/mod.rs` at `2847c42`, compared with `2c9a6470`). It also changes `agent_providers` to work without a project (`ops/agent.rs:22-29`). Without this MT, upstream's gate:
- denies the agent catalog in Settings opened from Welcome;
- denies Show Ignored Files in restricted projects;
- lets `vcs_ignored` take the Git executable from an untrusted project's settings;
- leaves a running suggestion alive after a revoke, because `AgentManager::shutdown` (ide-agent lib.rs:998-1005) stops only tasks, while `complete()` owns its session in a `CompletionScope` (lib.rs:444-529, :1912).

### 3.2 Fork command classification

- In `trust.rs`, `restricted_command_allowed` gains one call, `|| fork_restricted_command_allowed(cmd)`. That fork function lives in the same file, below upstream's list, with a comment naming this plan. Classification:

| Command | Restricted / no project | Reason |
|---|---|---|
| `agent_providers` | allowed | Reads the user's profile (`<config>/agents`, `models.json`, the registry cache). No spawn: `providers_from` (ide-agent lib.rs:254-275) and `AgentManager::providers` (:365-380) only read files. `provider::installed` (provider.rs:552-560) and `registry::mark_updates` (registry.rs:324-334) do stat/PATH lookups on the IDE process `PATH`, which no project setting changes. |
| `agent_set_args` | allowed | Writes only `<config>/agents/extra-args.json`. |
| `vcs_ignored` | allowed | The same read as `vcs_status`, protected as in 3.3. |
| `agent_complete` | needs trust | Starts an agent process. |

- `agent_providers` is the only row that is not fork-only: upstream registers it and guards it with `require_trust` (ops/agent.rs:19-24 (06109aae)). Listing it in the fork function is a deliberate override of upstream's behaviour, and section 6 checks it apart from the fork-only commands.
- `ops::agent::providers` drops the `require_trust` that the cherry-pick added. The Welcome fallback stays. `set_args` is fork-only and upstream never adds a guard to it, so the fork's `ops::agent::set_args` stays unchanged: do not add a guard only to remove it. Its witnesses: a direct `set_args` call that succeeds is a guard; the missing dispatcher classification is the behavioural RED; the combined catalog witness is RED through `providers`. (Coordinator clarification 2026-11-01, from dev-codex's MT-6 preparation C0D3B4.)
- `ops::agent::complete` calls `host.require_trust(window)?` before `agents.complete(..)`.
- `Host::authorize_command` stays as upstream wrote it (trust.rs:288-293 (06109aae)). An allowed command passes without looking up a project. Any other command looks up the window's project first: a window without a project gets `NotFound` ("no project is open in this window", lib.rs:119-124 (06109aae)), and a restricted project gets the Restricted Mode error. This plan does not change Host's error.

### 3.3 Show Ignored Files under restriction

### 3.4 Suggestion: refuse when restricted, cancel on revoke

`ide-agent` `Shared` gains `execution: parking_lot::Mutex<Execution>`, with `Execution { allowed: bool, epoch: CancellationToken }`; it starts allowed.

- `AgentManager::set_execution_allowed(allowed)` sets `allowed` under the lock. When `allowed` is false it also cancels `epoch` and replaces it with a fresh token.
- `shutdown()` does what `set_execution_allowed(false)` does, under the same lock: it sets `allowed = false`, cancels `epoch` and replaces it. Only an explicit `set_execution_allowed(true)` reopens admission. A request can keep an `Arc<Project>` past the close (`Host::project` returns a clone, lib.rs:119-124 (06109aae); `close_project` removes the project and calls `agents.shutdown()`, :145-151 (06109aae)), and `complete()` loads the provider and creates its directory before the connector call (ide-agent lib.rs:455-479). With admission closed, such a request cannot start an agent after the close. Upstream's `trust.rs` policy does not change.
- At the start of `complete()`, after the empty-prompt check and before `provider::load` and the temporary directory (lib.rs:455-473), `complete()` takes the lock. When execution is not allowed it returns `IdeError::unavailable` with upstream's exact text `"Project is in Restricted Mode. Trust the project to enable execution."`; otherwise it clones `epoch` under that lock. A refusal at the gate creates nothing that needs cleaning up. After a close, no window shows this text.
- `provider::load` and the temporary directory now sit between the gate and the connector, so a revoke or shutdown there would leave `complete()` holding a cancelled epoch. Right before the connector call (:479), `complete()` checks `epoch.is_cancelled()`. When it is cancelled, `complete()` runs `scope.finish().await` as on the other paths, which removes the directory, and returns the same restricted error without calling the connector.
- `complete()` then runs `tokio::select!` between `epoch.cancelled()` and the timed `ask(..)` together with the `TURN_GRACE` wait that follows a successful `ask` (lib.rs:493-521 on `next/v0.3.1`), so the whole session after the connector is cancellable, not only the `ask`. A cancellation becomes the restricted error. (Coordinator clarification 2026-11-01, from dev-codex's MT-6 preparation C0D3B4.) `scope.finish().await` runs as on every other path: `Peer::kill` (with the teardown tranche, the whole process tree ends), then removal of the `ibl-suggest-*` directory.
- The host sets the flag in two places. In `project.rs` `open_project`, it calls `agents.set_execution_allowed(trusted)` after `project_services` returns the manager (:337 (06109aae); `AgentManager::new` is in that helper, :400) and before the `Project` is built and published (:343 onwards), so no window can reach it first. In `trust.rs` `refresh_project_trust`, it calls `project.agents.set_execution_allowed(trusted)` in both branches; on revoke the call sits next to `lsp.set_execution_allowed(false)`, before `agents.shutdown()`.
- Each call to `complete()` ends one of two ways. Either it is refused before the connector, with zero connector calls: at the gate, leaving no directory, or at the re-check, after `scope.finish()` has removed the directory. Or it reaches the connector with an epoch that every later revoke or shutdown cancels, and `scope.finish()` then kills the peer and removes the directory. Since the flag and the epoch change under one lock, nothing falls between the two.

### 3.5 Frontend

Commit view:
- The Suggest button (CommitView.tsx:889-892) is disabled when `useProject` reports `trusted === false`, with the title "Trust the project to suggest commit messages."
- When trust turns false while a request is pending, an effect retires it at once and updates the view itself: `pendingSuggest.current = null`, `setSuggesting(false)`, and `setSuggestError(tx("Project is in Restricted Mode. Trust the project to enable execution."))`. The key is one of #517's strings (zh at 06109aae); Task 7 adds the Italian. The view cannot wait for the backend to show the error, because the `catch` sets the error only for the live request (:851).
- The guards on the late result (:847) and on the `catch` (:851) stay. A late answer or a late rejection then changes neither the draft nor the error shown.
- `finally` (:853-854) calls `setSuggesting(false)` unconditionally today. After a revoke and a re-trust, the old request would then clear the in-progress state of a new one. It must clear `suggesting` only while no newer request has started, for example by comparing `request` with a ref to the latest request started. A request retired by the effect at :793-798 (included files, Amend or repository changed) still clears `suggesting` when it settles, as now.
- Show Ignored Files (:511, `vcsIgnored` at :368) stays available in restricted projects.

Agents:
- `store.ts` keeps upstream's re-sync on trust change but loads `agentProviders()` in every mode. This replaces upstream's empty list for restricted projects, so Manage Agents, presets and arguments work there.
- `HomeEditor.tsx` `useProbe` (:276-289) does not probe while restricted, and the start action is disabled with "Trust the project to start agents." `AgentsView.tsx` disables New Session the same way.
- `MessageSuggestion.tsx` is unchanged, since it calls `agentProviders()` directly.

Fork-only test fixtures that build `ProjectInfo` add `trusted: true`, or `trusted: false` where a test covers restriction.

### 3.6 Settled without new code (tests and release notes)

- Migrated profiles. `TrustStore::load` imports recent projects as trusted when `project-trust.json` is missing (trust.rs:22-38). Profile seeding copies everything except `migrate.rs` `EXCLUDED` (:32), so a seeded `project-trust.json` keeps its decisions, and without one the seeded recent projects become trusted. Existing v0.3.0 users have no file, so their recent projects become trusted at the first v0.3.1 start. The design accepts this (section 4); Task 6 tests it and MT-7 puts it in the release notes.
- Remote protocol 2. The client installs the server of its own version (`remote_dev.rs` `ensure_server`, :200-240) and refuses another protocol with an explicit error (:329-338). An older `openidea-server` is incompatible; this goes in the release notes.
- PATH budget. The code does not change (upstream does not touch `ide-core/src/tool_path.rs` or `ide-tools/src/lib.rs`). In restricted projects, terminals drop the project's shell, args and env (#517 `ops/term.rs`), and `postStartCommand` does not run. Task 8 verifies the matrix.

## 9. Risks and NOT_VERIFIED

- Without the teardown tranche on the base, a revoke on Windows kills only the agent's leader process, and descendants such as Codex's `git ls-remote` chain can survive. That criterion stays NOT_VERIFIED until the tranche merges.
- The Windows positive controls rely on Git for Windows running configuration commands and hooks through its own `sh`, and on Rust running `.cmd` witnesses with the arguments Git and the probe pass. Checked on one Windows 11 machine with Git 2.45.1.windows.1, outside the IDE, in a temporary repository with the Task 3 configuration:
  - `git` resolved as `C:\Program Files\Git\cmd\git.exe`: all five controls created their markers (clean filter, textconv, external diff, fsmonitor, `#!/bin/sh` pre-commit);
  - `git` resolved as `mingw64\bin\git.exe`, with no `usr\bin` on `PATH`: none did.
  So the controls depend on which `git` the test process resolves. When they cannot run, the test fails, which is the intended outcome. The CI runner's Git stays NOT_VERIFIED until the dispatched run; if a control fails there, report it instead of weakening the test.
- Four of upstream's tests in `crates/ide-host/tests/trust.rs` are Unix-only (:66, :138, :178, :195 (06109aae)), and so is all of `trust_git_binary.rs` (`#![cfg(unix)]`, :2). A green `cargo test --test trust` on Windows does not show them; the fork's Task 3 tests carry the Windows coverage.
- Out of scope, upstream: task creation checks trust before it registers the task, so a revoke in between can miss a task that is just starting. Report it; it may be worth an upstream issue.
- Upstream behaviour this plan keeps, NOT_VERIFIED here (record what Task 8 shows):
  - the project environment overlay is process-wide, so a restricted window's terminal may see a trusted window's project environment;
  - the selected Git binary stays process-wide;
  - Settings opened from Welcome cannot use non-allowlisted commands such as tool installs.
- Behaviour changes for the release notes:
  - recent projects become trusted at the first v0.3.1 start;
  - an older `openidea-server` is incompatible (protocol 2);
  - Suggest is unavailable in Restricted Mode;
  - closing a project now also stops a running suggestion.
- Sync cost: the fork classification call in `trust.rs` and the `set_execution_allowed` calls in `trust.rs` and `project.rs` will reappear as conflicts in the next upstream sync.
