## 1. Context and goal

Two small defects were left open by the v0.3.0 sync (roadmap section "v0.3.x follow-ups"):

- `src/features/github/diff/reviewDiff.test.tsx:219` fails now and then ("expected null not to be null", CI run 41189578661 and local full runs). The test waits for inlay `T1` (`:207`) and then checks inlay `T2` synchronously (`:219`). When `T2` renders a tick after `T1`, the check fails.
- The module doc of `crates/ide-tools/src/lib.rs` (`:9-10`) still says that language servers find managed tools because `extend_process_path` puts every `tools_bin_dirs` entry on the process `PATH` at startup. Since the `PATH` budget tranche (#11), startup adds only the existing directories, and later installs are found through `ide_core::tool_path::search_path()`.

Goal: the test is deterministic and the doc matches the code. No product behaviour changes.

## 3. Solution design

- In `reviewDiff.test.tsx`, wait for `T2` the same way the test waits for `T1`: `await waitFor(() => expect(inlay("T2")).not.toBeNull())`. Do not change what the test asserts, and do not add sleeps or longer global timeouts. If other synchronous checks in the same file have the same pattern (a check on an element that renders asynchronously right after a `waitFor` on another one), fix them the same way and list them.
- In `crates/ide-tools/src/lib.rs`, rewrite only the two module-doc lines (`:9-10`) so they describe the current behaviour: at startup `extend_process_path` puts the managed bin directories that exist on the process `PATH` and registers the full candidate list; `search_path()` finds tools installed later. Code unchanged.
