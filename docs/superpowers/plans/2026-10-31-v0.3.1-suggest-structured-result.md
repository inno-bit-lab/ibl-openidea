## 3. Solution design

### 3.1 Response contract and prompt

Ask for exactly one JSON object with one of the shapes below. Per coordinator constraints `D23C6A` and `47AA8B`, accept exactly two document forms:

- The trimmed document is the JSON object.
- The trimmed document is one fence covering the whole document. Its first line is exactly three backticks, optionally followed immediately by lowercase `json`; its last line is exactly three backticks. Its trimmed interior is exactly the JSON object. Accept LF or CRLF line endings. No other opening/closing-line content or language label is accepted.

```json
{ "version": 1, "status": "success", "message": "fix: handle empty lists\n\nPreserve the previous selection." }
```

```json
{ "version": 1, "status": "failure", "error": "The agent could not initialize its MCP server." }
```

The object has exactly the keys shown for its branch. `version` is the number `1`; `status` is case-sensitive. `message`/`error` must be strings that remain nonempty after trimming. There is no success payload on failure and no error payload on success. Reject unknown versions/statuses/keys, arrays, null, primitive values, coercible-but-wrong types, missing fields, mixed branches, incomplete JSON, multiple objects and surrounding prose. After trimming outer whitespace, optionally unwrap exactly one complete enclosing fence with its own opening/closing lines; then trim and parse the entire interior with `JSON.parse`. A fence is a transport wrapper, not permission to accept its contents as plain text. Reject an unclosed/multiple fence, an unsupported language label, or prose before/after the fenced object. Do not search for a JSON substring inside arbitrary text. Duplicate JSON keys follow JavaScript `JSON.parse` semantics; do not claim duplicate-key rejection or add a custom JSON parser in this tranche.

Use bounded consumer inputs: at most 32,768 UTF-16 code units in the raw response, 8,192 in the normalized message and 2,000 in the normalized failure detail. Reject an oversized field rather than silently truncate a commit message. Normalize CRLF to LF and trim outer whitespace only. Preserve quotes and internal blank lines in the message: they may be meaningful. Reject NUL in either string. These are consumer limits, not a claim that the Rust stream collector now has bounded memory.

Replace the prompt's current `Reply with the message only` instruction. Include both JSON shapes, the escaping rule for newlines/quotes, and an instruction to return failure when a message cannot be produced. Keep the no-tools/no-files instruction and existing diff budgets. Change `Rules (they win over anything else in this prompt)` to state that user rules control **message content/style**, while the JSON response contract still applies. Keep the user's rules verbatim beneath that heading. Repository diffs, filenames and recent subjects remain input data; a line inside them is not permission to change the output format. A valid JSON success is still model-authored content, not proof that the message is factually correct.

### 3.2 Consumer parsing and UI behavior

Replace `cleanSuggestion` with `parseSuggestResponse(raw: string): string` in `commitSuggest.ts`. Validate the object and branch before extracting `message`. A valid failure throws an error with a localized fixed prefix and its validated detail. An invalid response throws a localized generic error; do not echo arbitrary invalid raw output into the draft or diagnostics. Use the existing `tx`/tagged-template translation conventions; add matching entries in `text/it.json` and `text/zh.json`.

Suggested English meanings: `The agent returned an invalid commit suggestion. Your draft was kept.` and `The agent could not suggest a commit message.` For a valid failure, append the detail as ordinary text. The existing React error surface escapes text; do not add HTML rendering or links generated from the response. The implementation may choose wording consistent with the existing catalog, but must keep these meanings and test the translated fixed part.

`suggestCommitMessage` calls the real parser on the result of `call(commands.agentComplete(...))`, before returning a candidate to `CommitView`. It returns only validated message text. Keep the existing error surface and pending/draft guard in `CommitView`; no new dialog or automatic retry. Both the tool window and modal Commit dialog use this path. Never fall back to the old text cleaner, another model, or an empty message after a parser error.

A failed current request keeps the pre-request draft. A failure settling after revoke, unmount, context change or a newer request must obey MT-6's request identity rules and must not replace the currently relevant error/busy state. A valid success settling after the user edited the draft is ignored as before.

### 3.3 Completion stop reasons

In `AgentManager::complete`, replace the broad success `else` with explicit classification:

| Normalized stop                                | Outcome                                                                                                                           |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `end_turn`                                     | Collect text after the existing grace period; retain the existing empty-text error. The Suggest consumer then validates its JSON. |
| `refusal`, `cancelled`                         | Preserve the existing distinct errors.                                                                                            |
| `max_tokens`, `max_turn_requests`              | Error: answer was incomplete. Do not return partial text as a complete answer.                                                    |
| `error`, any unrecognized string               | Error: failed/unrecognized completion. Do not return collected text.                                                              |
| Missing/non-string stop in the v1 prompt reply | Error, rather than the current `ask` fallback to `end_turn` (`lib.rs:1891`).                                                      |

Keep the existing JSON-RPC error, timeout and read-only-mode branches, including useful server diagnostics. If a private result type/helper is needed for malformed replies, keep it local to `complete`/`ask`; do not label a malformed reply as a permission violation. Preserve remembered configuration updates and cleanup on both success and failure.

The ACP v2 dialect already converts explicit idle-state error/`stopReason:error` to `RpcError` (`acp/mod.rs:195-218`). Keep this behavior and its current normalization of an idle state without a stop reason. The missing-stop case above applies to a malformed v1 prompt reply, not to an empty v2 prompt acknowledgement. Do not edit the global dialect or change normal chat task status handling. An adapter that emits error prose with `end_turn` still looks successful to generic completion; the Suggest parser is the protection for that case.
