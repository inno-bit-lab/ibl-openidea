**Goal:** a project opened while its root is being revoked or closed is never published with trusted execution that the current decision does not allow, and its `postStartCommand` runs only through the same lifecycle protocol as every other trust transition.

**Architecture:** construction runs with execution closed; publication comes next; then the open reconciles the current decision through the grant transition, under the project's transition lock and gate. Nothing is trusted before the project is visible to refresh snapshots, so a revoke cannot miss it.

**Tech stack:** Rust only (`ide-host`).

## Review Focus

1. No trusted execution exists before publication: the project's flag, LSP, repository flags and agent admission start restricted, and no environment overlay or post-start command is prepared before publication.
2. After publication, the open reconciles under `trust_transition` and `trust_gate` with the decision read inside the gate, exactly as a refresh does.
3. When a refresh already holds the new project's transition lock, the open does not reconcile. That refresh reads the store under the gate itself. At this base only refreshes take `trust_transition`; the review checks that this still holds.
4. The post-start command runs only from the grant transition, so it is ordered against later revokes and closes by the same locks.
5. `open_light` and the reuse path for an already open project (`project.rs:76-81`) are unchanged.

## 1. Context and goal

`open_project` (`crates/ide-host/src/project.rs:63-385`):
- reads the decision at :85 into `trusted`;
- prepares the environment and caches the post-start command at :86-87 (remote server only; `environment.rs:70-73`);
- sets LSP admission at :120-121 and the repository flags at :219-222 from that value;
- sets agent admission at :337-338;
- builds the `Project` at :343, publishes it at :381 and spawns the cached post-start command at :382-384.

A revoke whose refresh snapshot (`trust.rs:103`) runs between :85 and :381 does not see the project. The project is then published trusted while the store says restricted. The lint DDB93D also showed why a re-check after publication is not enough on its own:
- at :381 the `Arc` is visible with trusted execution, so another thread can acquire it and start work before any re-check;
- notebook and run paths are gated by `require_trust`, not by agent admission;
- the cached post-start command needs ordering against a later revoke or close, and a check followed by a spawn outside the gate can run late.

A re-read of the decision just before publication brings back the original problem: a revoke whose snapshot misses the unpublished project.

## 3. Solution design

### 3.1 Construction with execution closed

In `open_project`:
- `trusted` starts as `Arc::new(AtomicBool::new(false))`. The decision is not read before publication.
- The environment preparation at :86-87 is removed, and so is the cached `post_start`.
- LSP (:121), the repository flags (:219-222) and agent admission (:338) take that false value, as for a restricted project today.

Until the reconciliation, every trust-gated host operation of the new project refuses through `require_trust` (`project.rs:496-502`), notebooks and runs included, and agent admission is closed.

### 3.2 Publication, then reconciliation

After `insert_project` (:381):
1. `project.trust_transition.try_lock()`. `open_project` is synchronous and cannot await. The project has just been published, so at this base the only possible holder is a refresh that took it in a snapshot after publication. That refresh reads the store under the gate and applies the current decision itself. When `try_lock` fails, the open skips the reconciliation.
2. Holding the transition guard, under `trust_gate`: when `closed`, do nothing. Otherwise read `self.trust.trusted(&root)`. When it is true, run the grant transition of TRUST-RACES 3.3 step 2: swap `trusted`, `project.repos()`, `environment.project_opened` plus `spawn_post_start`, LSP and agent admission true. The trust-races plan should factor that step into one helper used by both callers; if it did not, this plan factors it.
3. Release the gate, then the transition guard. The open emits no `ProjectTrustChanged`: its caller gets the state from the returned project, as today. When a refresh did the reconciliation instead (step 1), that refresh emits the event.

The post-start command is spawned only by step 2, under the gate, so a later revoke or close is ordered after it, and a close that came first makes step 2 a no-op.

Why the single grant of an open cannot overlap a revoke's cleanup: a revoke cleanup exists only after a revoke transition has applied, which needs the project to be trusted first. The open's grant is the first transition the project can have, and refreshes take the transition lock for every later one.

### 3.3 Behaviour changes

- On the remote server, the project environment and the post-start command are applied at the reconciliation instead of before construction. Nothing project-controlled starts before that point, because execution is closed during construction.
- For a trusted project, a request that reaches the project between publication and reconciliation is refused as restricted. The desktop UI sends project requests only after `open_project` returns, which happens after the reconciliation.

## 9. Risks and NOT_VERIFIED

- Written by reading `5c3570c4` and the TRUST-RACES plan, before that plan was implemented. Every RED is a prediction. If TRUST-RACES changes the helper or lock names in review, this plan follows them.
- The post-start boundary under a race (a revoke or close between publication and reconciliation on the remote server) has no deterministic test. The post-start path changes this process's environment, which is why `remote_env.rs` is Unix-only and alone in its binary (:1-4), and integration binaries cannot see `cfg(test)` pause points. It is checked by reading: the spawn exists only in step 2 under the gate. NOT_VERIFIED by test.
- `try_lock` skipping the reconciliation relies on the refresh that holds the lock reading the store under the gate, which TRUST-RACES 3.3 guarantees. A future change that lets something other than a refresh hold `trust_transition` would break this assumption; the review checks it.
- Behaviour changes of 3.3: environment timing on the remote server, and refused requests between publication and reconciliation. Neither is visible in the desktop UI flow; NOT_VERIFIED on a real remote host.
- Sync cost: `open_project` is upstream code, so the construction and reconciliation changes will reappear as conflicts in the next upstream sync.
