**Goal:** close the two project-trust races that the v0.3.1 notes list as open:
- (a) trusting a project while it is being revoked or closed can leave agent admission out of step with the project's trust. One case reopens admission on a manager that `close_project` has already shut down.
- (b) an agent task that starts while trust is being revoked can still launch its agent, because the revoke and the task's registration interleave.

**Architecture:** no new policy. Three rules:
- Per project, a trust transition reads the decision and makes every admission and ownership change inside one synchronous critical section (`Project::trust_gate`). A per-project transition lock (`Project::trust_transition`) keeps a later grant from starting while a revoke's cleanup is still running. A closed project refuses every later transition.
- In `AgentManager`, a launch is admitted under the existing `execution` lock, and the launched peer is registered under the same lock with an epoch check. Until it is registered, the peer stays owned by the existing `Peer` RAII (`KillOnDrop`), and the new cancellation must preserve that. Session setup becomes cancellable without corrupting the task's resumable state.
- Closing a project is terminal in the agent layer (`AgentManager::close`). The revoke no longer calls `shutdown()`: it detaches what it owns under the gate and kills only that afterwards.

**Tech stack:** Rust only (`ide-host`, `ide-agent`). No IPC type, binding, frontend or locale change.

**Spec:** the MT-6 plan `b08054fc:docs/superpowers/plans/2026-10-31-sync-v0.3.1-mt6-trust.md` (sections 3.4 and 9), PR #22, the v0.3.1 release notes `5c3570c4:docs/releases/v0.3.1.md` ("Known limitations"), and the lint DDB93D. All line numbers below are for `5c3570c4`.

## Review Focus

1. All admission changes and ownership changes belonging to a trust transition happen in its synchronous critical section under `trust_gate`: the decision read, `project.trusted`, the LSP flag, agent admission and detachment (`AgentManager::revoke`), notebook admission (`restrict_admission`), the repository flags and the environment's opened/closed state. The revoke detaches or captures the resources it owns there. Cleanup outside the gate acts only on what it captured, or on resources that no later grant can have installed because the transition lock is still held (3.3). It cannot change admission or erase state installed by a later grant. The unchanged `AgentManager::shutdown()` is never called in a tail.
2. The gate is never held across `.await` and never held while calling `Peer::kill`, `AgentRevocation::finish`, `processes.kill_project`, kernel shutdown or `debugger.stop`, and the trust event is never emitted under it. It does include environment configuration I/O (`project_opened` reads `devcontainer.json`, `environment.rs:93-`), LSP scheduling (`ensure_started` spawns) and one possible emit: on the remote server, `load_project` sends a `Notify` for a malformed `devcontainer.json` (`environment.rs:93-97`). It is not a flag-only section.
3. Both directions take `trust_transition` before the gate. A revoke holds it through its whole cleanup. A grant releases it right after its gate section and takes it again only to emit its event.
4. `close_project` and `Host::shutdown` set `closed` under the gate before per-project teardown. `Host::shutdown` already stops the global environment, processes and terminals before that (`lib.rs:194-197`); this plan does not reorder them.
5. `AgentManager::close()` is terminal. `shutdown()` keeps today's reversible contract (`completion_runs_again_after_execution_is_allowed_again` stays green) and has no host caller after this plan.
6. Every connector call site (`complete`, `Task::ensure_session`, `probe`) is admitted through the `execution` lock. A newly connected peer that is not yet registered stays owned by the existing RAII: `Peer` holds `Arc<KillOnDrop>`, whose `Drop` cancels the kill token when the last clone drops (`ide-jsonrpc/src/lib.rs:318-332`, created at :682-683). The new `select!` and the registration preserve that ownership: before `register` returns true, no clone of the peer is moved anywhere that outlives the setup (a spawned task, a field, a cache), and every exit (setup error, epoch cancellation, refused registration, drop of the outer future) drops all its clones, with neither `execution` nor `trust_gate` held. No new peer guard or ownership type is added.
7. Session setup is cancellation-safe: `replaying` is reset on every exit, and a pending rollback is never consumed before its request succeeds. When the outcome is unknown, the saved session is invalidated (3.2). The rollback guard releases `state` before it calls `persist()`, which takes `state` itself (`lib.rs:1145`); `parking_lot::Mutex` is not reentrant. `forks_rollbacks_and_steering` (`tests.rs:859`) and `archived_tasks_can_be_restored_and_continue_their_session` (`tests.rs:1022`) stay green.
8. The `#[cfg(test)]` pause points compile to nothing in non-test builds and sit where 3.6 says, including their different positions in the RED baseline and after the fix.

## 1. Context and goal

MT-6 (PR #22, merged as `44dd5f5f`) ported upstream's project trust and added an execution gate to `AgentManager` for the throwaway Suggest session. The gate covers `complete()` only. Two races were left open and recorded as limitations in the v0.3.1 notes. The rev-claude MT-6 review (62ECD6) found (a); the PR #22 description and the MT-6 plan section 9 recorded (b). The lint DDB93D confirmed every interleaving below in the source, without a runtime reproduction.

### 1.1 Race (a): grant against close or revoke

`refresh_project_trust` (`crates/ide-host/src/trust.rs:102-146`) takes a snapshot of the open projects (:103). For each one it reads the decision (:104), swaps `project.trusted` (:105-108), and then applies side effects in separate steps: revoke flags (:109-112), `project.repos()` (:113), grant effects (:114-119), the revoke tail (:120-141), `lsp.reconfigure().await` (:142) and the event (:143). There is no per-project serialization and no closed state. `refresh_project_trust` is called from `set_project_trust` (:97-100) and from `project_trust_remove_location` (Tauri `src-tauri/src/commands/app.rs:299-302`, remote `crates/ide-host/src/rpc.rs:146-148`). These run as async commands on the multi-threaded runtime, so two refreshes, or a refresh and a close, can run at the same time without any `.await` in between.

#### a1: grant against close

Window W shows a restricted project P.
1. Thread G: `project_trust_set(P, true)` (`app.rs:283-295`) runs `decide` (trust.rs:98), then `refresh_project_trust`. Its snapshot (:103) contains P, the read (:104) returns true, and `swap(true)` (:105) returns false, so G goes on.
2. Thread C: `close_project(W)` (`src-tauri/src/commands/app.rs:109-113`, or `WindowEvent::Destroyed` at `src-tauri/src/lib.rs:188-194`, or `remote_dev.rs:347`) reaches `Host::close_project` (`crates/ide-host/src/lib.rs:145-157`). It removes P from the map (:146) and calls `agents.shutdown()` (:151), which closes admission (`crates/ide-agent/src/lib.rs:1053`). It then spawns `lsp.shutdown_all()` (:154-155).
3. G continues with `project.repos()` (trust.rs:113). On the remote server only (`environment.rs:70-73` returns `None` unless `project_env`), it also runs `environment.project_opened` and `spawn_post_start` (:115-116), recording an open project and starting its `postStartCommand` after the close. It then calls `lsp.set_execution_allowed(true)` (:118) and `agents.set_execution_allowed(true)` (:119).
4. P's `AgentManager` is admitting again, but P is no longer in the map, so no later revoke or close will ever shut it down. Any holder of an `Arc<Project>` can now start agents on P. One such holder is `ops::agent::create` (`crates/ide-host/src/ops/agent.rs:123-132`), which keeps `project` across the `validate_project_root` await (:129) before calling `project.agents.create` (:131). The agents run until the app exits. For LSP the outcome depends on timing: `ensure_started` refuses once `shutting_down` is set (`crates/ide-lsp/src/lib.rs:425-428`), but `close_project` only spawns `shutdown_all` (:2301-2305), so a grant that runs before that task sets the flag can start a server that then races with `shutdown_all`.

#### a2: grant against revoke

P is restricted.
1. G: `decide(true)`, then the refresh reads true (:104) and swaps (:105, previous false).
2. R: `decide(false)`, then the refresh reads false and swaps (previous true). R runs the revoke: flags false (:110-111), `agents.shutdown()` (:122), `kill_project` (:123), the notebook, request and debugger tail, and emits `ProjectTrustChanged { trusted: false }`.
3. G resumes and runs the grant effects: `lsp.set_execution_allowed(true)` and `agents.set_execution_allowed(true)` (:118-119). It then emits `{ trusted: true }`.
4. The final state is mixed. The store and `project.trusted` say restricted, so host operations refuse through `require_trust` (`project.rs:496-502`). Agent and LSP admission are open, and the last event tells the UI the project is trusted. Language servers configured by the project can start on the next file open (`lsp/lib.rs:2039-2052`), and retained-`Arc` paths can start agents.

The same steps with G and R swapped give the opposite case: the revoke lands last and the project ends restricted although the last decision was a grant.

#### a2r: a stale revoke tail after a later grant (lint B1)

Revision 1 serialized only the first flag writes, which leaves this schedule open: R applies its revoke flags and releases; G applies the newer grant; then R's unlocked tail runs. That tail calls `agents.shutdown()`, which cancels G's new epoch (:1053), kills agents launched after G (:1054-1058) and clears the sink (:1059). It also runs `environment.project_closed` (`environment.rs:80-89`), which erases the environment G installed, plus `kill_project`, the kernel shutdown and the debugger stops, all of which act by path or by window on resources G's grant may have started. The final store, project flag and event say trusted, but agent admission is closed. A later refresh finds nothing to change and does not repair it.

### 1.2 Race (b): task start against revoke

The host operations check trust once, at the start (`ops/agent.rs:124, :136, :147, :159, :165, :171`). `AgentManager` itself admits only `complete()` (`ide-agent/src/lib.rs:476-482`). Nothing else consults `Execution`, and `shutdown()` (:1052-1060) can only kill agents that are already registered in `task.live`.

#### b1: revoke during `create`

1. `agent_create` (`src-tauri/src/commands/agent.rs:124-126`) runs `ops::agent::create`, which passes `require_trust` (`ops/agent.rs:124`) and awaits `validate_project_root` (:129). `AgentManager::create` then awaits the worktree or snapshot step (`lib.rs:587-608`).
2. The revoke runs `agents.set_execution_allowed(false)` (trust.rs:111) and `agents.shutdown()` (:122). `shutdown` iterates `self.tasks` (lib.rs:1054), but the new task is not there yet.
3. `create` inserts the task (:652) and spawns `handle.run` (:655). `run` calls `turn` (:1205), then `ensure_session` (:1320), then the connector (:1414). The agent starts in a restricted project and keeps running.

Separately, a `create` admitted before the revoke can enqueue blocking work whose Git commands begin after the revoke (`create` :597; `worktree.rs:29-49`). Worktree creation performs revision and branch operations and `worktree add` through fresh `Repo` instances with execution enabled (`ide-vcs/src/repo.rs:51`), so hooks may run. This plan does not cancel that work, and it does not bound its duration or hook effects (section 9).

#### b2: revoke while a task's session starts

1. A trusted task runs `ensure_session` (`lib.rs:1388-1517`): it takes `connecting` (:1389), calls the connector (:1414), then awaits `initialize` (:1418) and the session setup. It stores `live` only at :1515.
2. The revoke's `shutdown()` calls `task.kill()` (:1055), which takes `live` (:1756). `live` is still `None`, so nothing is killed.
3. `ensure_session` finishes and stores `live` (:1515). The agent process stays alive, and `turn` sends the prompt (:1347).

The same window opens through `prompt` (:692), `send_queued_now` (:740), `fork` (:799) and `rollback` (:862), because each one reaches `ensure_session`. The setup also has fallible exits before :1515 (`initialize` at :1418, `session/new` at :1442-1449). On those exits, and when the outer future of `fork`, `rollback` or `probe` is dropped, the peer is not registered, but the existing `Peer` RAII ends it when its last clone drops (`ide-jsonrpc/src/lib.rs:318-332`). The lint withdrew its B2 for this reason (E90C3B); the plan only has to keep that ownership intact.

#### b3: revoke during `probe`

`probe` (`lib.rs:892-955`) calls the connector (:912) and waits up to `PROBE_TIMEOUT` (30 s, :55) for `initialize` (:922) before killing the peer (:923). The peer is never registered, so a revoke cannot stop it early, and a probe admitted just before the revoke starts its agent afterwards.

## 3. Solution design

### 3.1 Agent layer: admission, ownership and terminal close

In `crates/ide-agent/src/lib.rs`:

- `Execution` (:97-100) gains `closed: bool`, false at construction (:341). `set_execution_allowed(true)` does nothing when `closed` is set; `set_execution_allowed(false)` still cancels and replaces the epoch.
- `pub fn close(&self)`: under `execution`, `closed = true`, `allowed = false`, cancel and replace the epoch. Then the same kill/persist loop and sink clear as `shutdown()` (:1054-1059). `shutdown()` does not change.
- `pub fn revoke(&self) -> AgentRevocation`, called by the host under `trust_gate`. Under `execution`: `allowed = false`, cancel and replace the epoch; release. Then, for each task of `tasks.read()`: `cancel_permissions()` (:1737-1741, it only drains reply channels) and `live.lock().take()`. It returns the captured peers and the task handles. It neither kills nor clears the sink.
- `AgentRevocation::finish(self)`, called after the gate is released: kill each captured peer, then persist each captured task. It never touches `Execution` or the sink, so a later grant's epoch, agents and subscription survive it.
- `Shared::admit(&self) -> IdeResult<CancellationToken>`: under `execution`, the epoch's clone when `allowed`, otherwise `IdeError::unavailable(RESTRICTED_EXECUTION)`. `complete()` may switch its inline block (:476-482) to it; nothing else in `complete()` changes.
- `Shared::register(&self, epoch, store: impl FnOnce()) -> bool`: under `execution`, run `store` and return true when the epoch is not cancelled. The closure only stores `live` (order: `execution`, then `Task::live`). It never kills.
- `create` (:578): `self.shared.admit()?` before anything else, so a closed or restricted manager creates no worktree, snapshot or task. The advertised outcome is narrow: a task that reaches launch while admission is still closed ends `Failed` with the restricted message. A revoke followed by a re-grant before launch lets the launch run in the new epoch, as `prompt`, `fork` and `rollback` already do after their host check. The plan does not carry the creation epoch to the first launch.
- `Task::ensure_session` (:1388): after taking `connecting`, `let epoch = self.shared.admit()`. From `initialize` (:1418) to the end of the setup (:1513), the setup runs inside `tokio::select! { biased; _ = epoch.cancelled() => .., setup => .. }`. The cancelled branch, every setup error and a drop of the outer future drop the setup future, and with it the connection's only `Peer` clones, so the existing `KillOnDrop` ends the agent (RF6). The store at :1515 becomes `register(&epoch, || *self.live.lock() = Some(live.clone()))`. On false, `live` and the connection are dropped after the lock is released (an explicit `peer.kill()` there is also fine), and the restricted message is returned.
- `probe` (:892): `self.shared.admit()?` before the connector (:912), and `initialize` (:922) inside the same `select!`. On cancellation it kills the peer (or drops its only clone) and returns `IdeError::unavailable(RESTRICTED_EXECUTION)` without caching a probe. The existing kill (:923) stays on the normal path.
- Host callers: `Host::close_project` (`lib.rs:151`) and `Host::shutdown` (:201) call `agents.close()`. The revoke uses `revoke()` and `finish()` (3.3). No host code calls `shutdown()` any more.

A launch admitted after a revoke makes no connector call. A launch admitted before it may already have called the connector, and then ends in one of these ways: on cancellation, setup error or drop, its last `Peer` clone is dropped and `KillOnDrop` ends it; or its registration finds the epoch cancelled and the dropped clones end it; or its registration came first, so `revoke()` or `close()` captures it and `finish()` or the close loop kills it. The last case holds because the cancel and the registration exclude each other under one lock, and the capture reads `live` after the cancel. The plan does not promise zero connector calls for launches admitted before the revoke.

### 3.2 Cancellation-safe session setup (lint B3)

The `select!` of 3.1 makes stateful awaits cancellable. They must not corrupt what the task resumes from:

- `replaying` (set at :1426, reset at :1430; updates are suppressed while it is set, :1574, :1580, :1639): a scope guard resets it on every exit of the load step.
- `pending_rollback` (taken at :1455 before the `_openidea/rollback` request at :1459): read it without taking it. On `Ok`, set it to zero. On `Err`, keep today's behaviour: warn and set it to zero. A rollback guard covers the request itself: if the request is dropped before it returns, the remote outcome is unknown. The guard then sets `session_id = None` and `pending_rollback = 0` in one `state.lock()`, releases that lock, and calls `persist()` synchronously before it returns (`persist` takes `state` itself, `lib.rs:1145`, and `parking_lot::Mutex` is not reentrant). A concurrent close or revoke `persist` therefore cannot save the stale pair after the guard has run. The next `ensure_session` finds no saved session and opens `session/new` (:1440); the forked conversation keeps its entries. This defines the recovery before another turn is admitted, and it never repeats a relative rollback that may have been applied. There is no new user-visible string, only a `tracing::warn!`.
- `config_sent` (filled at :1489 before each set request) is cleared at the start of every `ensure_session` (:1401), so a cancelled setup leaves nothing for the next one. A `session/new` whose reply is lost leaves an orphan agent-side session, which is harmless. `session_id` is written only at :1510, after the setup.

### 3.3 Host layer: transition lock and critical section (races a1, a2, a2r)

- `Project` (`crates/ide-host/src/project.rs:21`) gains `pub(crate) trust_gate: parking_lot::Mutex<TrustGate>` with `TrustGate { closed: bool }`, and `pub(crate) trust_transition: tokio::sync::Mutex<()>`. Both constructors initialise them (`open_project` :343, `open_light` :461).
- `NotebookService::restrict` (`crates/ide-host/src/notebook.rs:410-426`) splits into `restrict_admission(&self)`, which is its synchronous half (:411-418: generation increment and batch cancel), and `shutdown_kernels(&self).await`, which is the rest (:419-425). `restrict` has one caller (trust.rs:124).
- `refresh_project_trust`, per non-light project of the snapshot:
  1. `let transition = project.trust_transition.lock().await;`
  2. Under `trust_gate`: when `closed`, skip the project. Read `self.trust.trusted(&project.root).unwrap_or(false)` here. When `project.trusted.swap(..)` returns the same value, skip. Otherwise:
     - revoke: `lsp.set_execution_allowed(false)`, `let revocation = agents.revoke()`, `notebooks.restrict_admission()`, `project.repos()`, `environment.project_closed()`;
     - grant: `project.repos()`, `environment.project_opened` plus `spawn_post_start` (it only starts a thread, `environment.rs:151-157`), `lsp.set_execution_allowed(true)`, `agents.set_execution_allowed(true)`.
  3. Revoke, still holding `transition`, with the gate released: `revocation.finish()`, `processes.kill_project` (blocking on Windows: `taskkill ... .status()`, `ide-run/src/process.rs:874-883`), `notebooks.shutdown_kernels().await`, the request and debugger steps (:125-140), `lsp.reconfigure().await`, then the event (step 5). Release `transition`.
  4. Grant: release `transition` right after step 2, run `lsp.reconfigure().await` without it, then take `transition` again for the event (step 5) and release it.
  5. Event: under `transition`, read `closed` and `project.is_trusted()` under a brief gate acquisition, release the gate, and when not closed emit `ProjectTrustChanged { trusted }` with that value. Events are therefore serialized and each carries the state at emit time. One residual: a close between that read and the emit produces one event for a project that has just closed, which is harmless.
- `Host::close_project`: right after the removal (:146), `project.trust_gate.lock().closed = true;`, then the existing sequence with `agents.close()`. It is synchronous and does not take `trust_transition`: a refresh waiting on that lock will find `closed` under the gate. `Host::shutdown` (:198-202) does the same for each drained project, after the global stops at :194-197.

Why this differs from the lint's capture model. Capturing every resource under the gate would need new APIs outside this crate pair: `processes.kill_project` kills by path and blocks on Windows (`process.rs:647-655, :874-883`); the kernel shutdown acts by path (`ide-notebook/src/kernel.rs:230-252`); and `lsp.reconfigure` in its restricted branch stops every instance (`lsp/lib.rs:2054-2058`). The transition lock instead guarantees that no later grant exists while a revoke's cleanup runs, so cleanup acting by path or by window cannot reach a grant's resources. The agent layer still follows the capture wording, because that is where the lint's counterexample hit (epoch, sink, kill loop).

Why the last decision wins, after the participating refreshes complete. Every `decide` is followed by its own refresh. That refresh takes the project's transition lock and then the gate after the `decide` has been written, and reads the store under the gate. Transitions on one project are serialized by the transition lock (grant gate sections, revoke gate sections with their cleanup), so the last of them to run reads the final decision. `decide` itself does not take the gate, so convergence holds after the refreshes complete, not at the instant of `decide`.

Why a revoke never waits while the project is trusted. The transition lock is held by a revoke for its gate section and cleanup, which run while the project is restricted; by a grant only for its gate section and its event, which are short and contain no wait; and by nobody else. A revoke that queues behind another revoke's cleanup finds the project restricted. One that queues behind a grant's gate section waits for one synchronous section. And when it queues behind a grant that is itself waiting for a revoke's cleanup, the project is restricted during that wait. Example: R1's cleanup runs, G and then R2 queue. After R1, G reads the store; if R2's `decide` came after G's, G reads false and changes nothing; then R2 reads false and changes nothing. The cost is availability: a grant waits for an unfinished revoke cleanup, so a stuck `debugger.stop` or kernel shutdown keeps the project restricted (section 9).

### 3.4 Lock order and why nothing deadlocks

1. `Project::trust_transition` (tokio). Taken only by `refresh_project_trust`, never while any synchronous lock is held, and at most one at a time per refresh (projects are processed one after another and each lock is released before the next project). Nothing called while it is held calls `refresh_project_trust` or `set_project_trust`.
2. `Host::projects` (`lib.rs:70`). Every user takes and drops it within one statement (`lib.rs:115, :121, :146, :198, :246`; `trust.rs:126-131`), so it is never held while another lock is taken. The window lookup of the revoke cleanup (trust.rs:125-131) runs in step 3, outside the gate.
3. `Project::trust_gate` (parking_lot). Taken by refresh steps 2 and 5, by `close_project` and by `Host::shutdown`. Never held across `.await`, never by `ide-agent`, `ide-lsp` or `ide-notebook` code, which do not know `Project`.
4. Locks taken under the gate, each without awaiting: `TrustStore::state` (`trust.rs:18`; `decide` and `remove_location` hold it across `persist` but never take the gate, so the order is always gate, then store), `Environment::state`, the LSP `servers` lock, the notebook registry and document state, `AgentManager::execution`.
5. `AgentManager::execution` (`ide-agent/src/lib.rs:85`): taken by `set_execution_allowed`, `close`, `revoke`, `admit`, `register`, each without awaiting. `register` takes `Task::live` inside it. `revoke()` releases it before reading `tasks`. No code holds `tasks`, `live` or `Task::state` and then takes `execution`.
6. Leaves: `AgentManager::tasks`, `Task::live`, `Task::permissions`, `Task::state`.

Cleanup is not lock-free everywhere. `Task::kill` holds `live` while it calls `Peer::kill` (:1756-1757), and `shutdown()`/`close()` hold `tasks.read()` while they kill and persist (:1054-1058). `AgentRevocation::finish` kills with no agent lock held. At `5c3570c4`, `Peer::kill` closes the transport and cancels the kill token (`ide-jsonrpc/src/lib.rs:755-757`); the process-tree termination runs through `spawn_blocking` (:763-768). Transport closure is not proof that OS descendants have exited.

`complete()`, its epoch and the teardown do not change. `complete()` holds `execution` only in its admission block; its `select!` (:564-568) and `scope.finish().await` (:569) hold nothing. `ensure_session` holds the `connecting` tokio mutex (:1389) across awaits, and `register` is a short synchronous section inside it; no code takes `connecting` while holding `execution`. `close_project` is synchronous (Tauri command, `Destroyed` event, `remote_dev.rs:347`) and takes only synchronous locks. The trust event is emitted outside the gate. The sinks are `NullSink` (`ide-core/src/event.rs:248`), `PeerSink` (`ide-host/src/rpc.rs:266-272`, a `peer.notify`) and `TauriSink` (`src-tauri/src/events.rs:13-17`, `emit_to`); none of them calls back into trust or takes the gate, by reading.

### 3.6 Test seams and test contract

The races exist only between two statements, so a deterministic RED needs a stop there. The lint accepted narrowly scoped `#[cfg(test)]` pause points on these conditions:

- New `#[cfg(test)] mod pause` in `ide-agent` and in `ide-host` (one file each). `arm(key, name)` returns a handle with latched `reached` and `release` states (a flag plus `Notify`, or a `watch` channel), so a waiter that arrives late still sees them. An arm is one-shot: the first caller with that exact key and name consumes it before parking, and every later caller passes. The key is the project root (host) or the store directory (agent), so parallel tests in one binary never share an arm. `observe` is an arm whose `release` is latched at creation: it records `reached` and does not park.
- Each test owns a `Pauses` guard. On drop, including on panic or timeout, it releases every arm and aborts and joins the tasks it spawned, so a behavioural RED cannot hang the runtime teardown.
- A test that waits for a task status after `shutdown`, `close` or `revoke` subscribes again (`mgr.subscribe(recording_sink)`) before it releases the paused task, because `shutdown`/`close` clear the sink (:1059) and the status may otherwise be emitted with no observer.
- Positive-control connector counters (`agent.cwds`, `agent.servers`, `agent.prompts`) are cleared before the action under test, never after it, as `completion_control` does (`tests.rs:2094-2101`).
- Bounded deadlines only fail a RED quickly, as `cancelled_completion` does (:2118-2133). None orders events.
- Pause points:
  - `ide-agent` `create:before-insert`: before `self.tasks.write().insert` (:652).
  - `ide-agent` `session:before-register`: in `ensure_session` after the setup and before the registration (today :1515).
  - `ide-host` `refresh:apply`. Baseline (Task 1 commit): after the swap (:105-108), before the first side effect. After the fix: after `trust_transition` is acquired and before the gate.
  - `ide-host` `refresh:after-gate`. Baseline: at the start of the revoke branch (:120), after the revoke flag writes and `repos()` (:109-113) and before `environment.project_closed()` (:121). After the fix: after the gate section, still holding `trust_transition`, before `revocation.finish()`.
  - `ide-host` `refresh:blocked` (`observe`), after the fix only: `#[cfg(test)] if transition.try_lock().is_err() { pause::observe(..) }` right before `trust_transition.lock().await`. The baseline has no lock, so tests that use it resolve on the competing future's completion instead (Task 3).
- `FakeAgent` (`crates/ide-agent/src/tests.rs:19-40`) gains one `hold: Mutex<Option<Hold>>` option, `Hold { method, reached, release }`, one-shot and latched like the pauses. The handler for `method` (`initialize`, `session/new`, `session/load` or `_openidea/rollback`) signals `reached` and then blocks until it is released or the connection closes, the way `hold_prompts` does (:293-298).
- Test names are fully qualified, as `--list` prints them: `tests::<name>` for `ide-agent`, `trust::races::<name>` for the new host unit module (end of `crates/ide-host/src/trust.rs`), and `--test trust_fork <name>` for the integration binary. Every exact invocation must report exactly one non-ignored executed test. Zero tests is a failure, even with exit 0.
- No compile failure counts as a behavioural RED.
- The `races` helper builds a `Host` as `crates/ide-host/tests/trust_fork.rs:8-20` does, with a recording sink like `crates/ide-host/tests/remote_env.rs:18-22`, and a profile witness agent as `trust_fork.rs:22-43`.

## 9. Risks and NOT_VERIFIED

- This plan was written by reading `5c3570c4`. No test was run while writing it, so every RED in section 7 is a prediction until the developer records it.
- Design choice for the re-lint: the per-project transition lock replaces capture APIs in `ide-run`, `ide-notebook` and `ide-lsp` (3.3). Its cost is availability: a grant waits for an unfinished revoke cleanup, so a stuck `debugger.stop` or kernel shutdown keeps the project restricted until that cleanup ends or the app restarts. This errs on the restricted side and is NOT_VERIFIED under a real hang.
- Open limitation: a revoke that races `open_project` can publish the project trusted while the store says restricted (`project.rs:85` against :381; on the remote server the `postStartCommand` also runs, :382-384). The dependent plan `2026-11-01-v0.3.2-trust-open-race.md` covers it. The v0.3.2 notes keep it until that plan is merged and verified.
- A `create` admitted before a revoke can enqueue blocking work whose Git commands begin after the revoke. Worktree creation performs revision and branch operations and `worktree add` through fresh execution-enabled `Repo` instances (`create` :597, `worktree.rs:29-49`, `repo.rs:51`), so hooks may run. This plan does not cancel that work, and its duration and hook effects are not bounded here. It is a separate finding for the coordinator.
- Check-then-act stays in every other host operation: one operation admitted before a revoke can finish after it. This plan targets agent processes that would outlive the revoke and stale cleanup, not every short operation.
- The gate's latency includes iterating the registered repositories in `Project::repos` (`project.rs:577-582`, no filesystem scan) and the configuration I/O of `environment.project_opened` on the remote server. A concurrent `close_project` of the same project waits for it. NOT_VERIFIED on large multi-repository folders.
